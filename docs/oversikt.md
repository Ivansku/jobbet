# Jobbet — Projektöversikt

*Senast uppdaterad: 2026-08-22 (Uppgiftsformulären konsoliderade till en delad komponent, ny fältgruppering)*

Detta dokument är en levande sammanfattning av vad appen gör och hur den är uppbyggd, på VAD/VARFÖR-nivå — för planeringssamtal, inte som teknisk referens. Uppdatera det när större funktioner läggs till eller avgränsningar ändras, inte vid varje commit.

## Tech stack

- **Frontend/Backend:** Next.js 16, App Router, TypeScript, Tailwind CSS, server actions för mutationer
- **Databas/Auth:** Supabase (Postgres + Row Level Security, Auth via Google OAuth — enda inloggningsmetoden)
- **Hosting:** Vercel, auto-deploy från GitHub main-branch
- **Extern integration:** Ett API-endpoint tar emot webhook-anrop (troligen från Power Automate) som synkar Outlook-kalenderhändelser till uppgifter, se nedan

## Datamodell (nuvarande)

| Entitet | Syfte |
|---|---|
| `foretag` | Tenanten. Har en e-postdomän — används sannolikt för att skilja interna kollegor från externa kontakter. |
| `person` | Interna användare, kopplade till Supabase auth. `roll`: admin/medlem. Har en separat Outlook-mailadress (skild från Google-inloggningsmailen) — troligen för att koppla kalenderhändelser till rätt intern person. `arbetstimmar_per_vecka` (standard 40) driver kapacitetsvisningen i Uppgifter-vyn. |
| `kund` | Bara namn på kundnivå. |
| `kontaktperson` | Kontaktpersoner kopplade till en kund: för-/efternamn, e-post, "senast kontaktad"-datum (redigerbart manuellt eller satt via import). Mailto-ikon i UI. |
| `kund_anteckning` | Manuella, fristående anteckningar på en kund — titel, datum, markdown-innehåll. Oberoende av `uppgift`/mötessystemet, redigeras direkt inline på kundkortet. |
| `kund_anteckning_deltagare` | Kopplar en `kund_anteckning` till en eller flera kontaktpersoner — samma delete+insert-synkmönster som `uppgift_deltagare`. |
| `uppgift` | Titel, beskrivning, status, prioritet, deadline, klockslag, tidsåtgång i timmar, ansvarig person, kund, taggad med uppgiftstyp och kategori, valfritt kopplad till ett `projekt` (`projekt_id`), manuell sorteringsordning inom dagskolumn, samt fält kopplade till Outlook-synk (event-id, `outlook_ical_uid` som stabil fallback-nyckel när Exchange byter event-id för samma möte, ursprunglig deltagarlista som text). `ar_placeholder` (boolean, default false) — se Placeholder-rader nedan. `anteckningsmall_id` (nullable, ärver typens standard när null) sätts bara vid projektgenerering — se Anteckningsmallar nedan. `utan_anteckningsmall` (boolean, default false) tvingar fram "ingen anteckningsmall" oavsett `anteckningsmall_id`/typens standard — enda sättet att uttryckligen slå av anteckningar på en uppgift, eftersom tomt `anteckningsmall_id` redan betyder "ärv typens standard". `mall_uppgift_id` (nullable, SET NULL om mall-uppgiften tas bort) spårar vilken uppgiftsmall-rad en instansierad uppgift kom från — sätts av `skapaUppgifterFranMall`, används bl.a. för att synka om en redan skapad uppgifts anteckningsmall-fält mot en uppdaterad mall-uppgift i efterhand (manuell, engångs SQL-synk, inget UI ännu). |
| `uppgift_serie` | Återkommande uppgifter: startdatum, slutdatum, veckodagar, intervall (var N:e vecka), standardvärden (typ, prioritet, kategori, tidsåtgång, klockslag) som kopieras till varje ny förekomst. Saknar fortfarande koppling till `projekt` — bara vanliga (icke-återkommande) uppgifter kan höra till ett projekt. |
| `uppgift_deltagare` | Kopplar uppgifter (möten) till en eller flera kontaktpersoner — sätts manuellt via en deltagarväljare eller automatiskt av Outlook-synken. |
| `uppgiftstyp` | Fri, admin-hanterad lista med typer för att märka uppgifter (t.ex. "Möte", "Support"). `anteckningsmall_id` (nullable FK till `anteckningsmall`, "Visa anteckningar" i formuläret) styr om och med vilken anteckningsmall som standard uppgifter av typen visar anteckningssektionen — t.ex. pekar "Maildialog" på en dedikerad "Mailinnehåll"-mall med ett enda block, så maildialoger antecknas genom samma blocksystem som mötesanteckningar istället för ett eget fält. |
| `kategori` | Fri, admin-hanterad lista för att gruppera/tagga uppgifter — ett lättviktigt taggningssystem. Hette tidigare `uppgiftsprojekt`; döpt om (databas, kod och UI) för att inte krocka begreppsmässigt med `projekt` nedan. |
| `anteckningsmall` | Admin-hanterad grupp av anteckningsblock (t.ex. "Standard", "Kundmöte") — se Anteckningsmallar nedan. |
| `anteckningsblock` | Admin-hanterad, rubricerad sektion för anteckningar (t.ex. "TODO", "Återkoppling"), hör till exakt en `anteckningsmall` (`anteckningsmall_id`, satt vid skapande, byts inte). Per block: sortordning (skopad inom mallen), aktiv/inaktiv. Valfri kort `beskrivning` — en instruktionstext till den som antecknar (t.ex. vad som ska frågas om under mötet) — visas som hjälptext under blockets rubrik i anteckningssektionen. |
| `uppgift_anteckning` | En anteckning per block och mötesuppgift (markdown, autosparas). `uppgift_id_genererad` är en kvarleva från den borttagna auto-genereringsfunktionen (se Byggt hittills) — pekar på en tidigare skapad uppföljningsuppgift när en sådan historiskt skapats och visas som en länk i notisen, men inget skriver till fältet längre. |
| `projekt_anteckning` | En anteckning per block och **projekt** (markdown, autosparas) — samma form som `uppgift_anteckning`, men delad mellan alla uppgifter i projektet istället för knuten till en enskild uppgift. Vilka block som visas avgörs av `projekt.mall_projekt_id → mall_projekt.anteckningsmall_id` (live-uppslag, inget eget fält på `projekt`) — se Projektanteckningar nedan. |
| `projekt` | Container för uppgifter — namn, valfri kund (`kund_id`, nullable — interna projekt tillåtna), status (planerat/aktivt/pausat/avslutat), beskrivning, startdatum, samt `mall_projekt_id` som spårar vilken mall projektet genererades från (SET NULL om mallen tas bort). Uppgifter pekar tillbaka via `uppgift.projekt_id` (SET NULL vid radering — "Ta bort projekt" kopplar bara loss uppgifterna, en separat "Ta bort projekt och alla uppgifter" raderar dem explicit). Att skapa ett projekt med mall skapar inte längre mallens uppgifter direkt — projektet kan finnas med mallen kopplad men utan uppgifter (t.ex. "planerat men ej fastställt", där första mötesdatumet inte är känt än). Uppgifterna instansieras genom en separat, explicit åtgärd ("Skapa uppgifter från mall"-knappen i projektmodalen, synlig när projektet saknar uppgifter), oberoende av status — inte automatiskt vid statusbyte, för att undvika oavsiktlig dubbelgenerering om status växlar fram och tillbaka. `farg` (nullable text, CHECK-constrained till en fast palett av 18 namngivna toner, se Projektfärg nedan) sätts via en färgväljare i "Redigera projekt" och styr uppgiftskortens bakgrundston i Uppgifter-Kanban. |
| `projekt_medlem` | Finns kvar i schemat men används fortfarande inte i appen — ingen egen projektägare/medlemslista oavsett enskilda uppgifters ansvariga. |
| `mall_projekt` / `mall_uppgift` | Projektmallar (t.ex. "Uppstart") och deras uppgiftsmallar. Varje uppgiftsmall har samma fält som en vanlig uppgift (titel, beskrivning, typ, kategori, prioritet, status, ansvarig-standard, tidsåtgång) förutom att deadline ersätts av `dagar_efter_start` — för första uppgiften i mallen räknat från projektets startdatum, för alla efterföljande kedjat från föregående uppgift i mallen (ordningen sätts av `sortordning`, omflyttningsbar). Ingen koppling till återkommande-fälten. `mall_uppgift.ar_placeholder` — se Placeholder-rader nedan. `mall_uppgift.anteckningsmall_id`/`utan_anteckningsmall` (nullable override av typens standardmall respektive tvingad "ingen mall", se Anteckningsmallar nedan) kopieras till den genererade uppgiftens motsvarande fält vid `skapaUppgifterFranMall`. `mall_projekt.anteckningsmall_id` (nullable FK till `anteckningsmall`) är den **projekt-delade** anteckningsmallen — se Projektanteckningar nedan, skild från `mall_uppgift.anteckningsmall_id` som styr den uppgifts-lokala mallen. `mall_projekt.kategori_id` (nullable FK till `kategori`, satt en gång i mallformuläret) representerar mallens "typ" som ett kategorivärde (t.ex. mallen "Uppgradering" ↔ kategorin "Uppgradering") — förifyller kategori på nya `mall_uppgift`-rader i mallen, och på nya uppgifter i Uppgifter-vyns formulär när man väljer ett projekt som genererats från mallen (bara om kategorifältet fortfarande är tomt, skriver aldrig över ett gjort val). Kopieras aldrig tillbaka eller synkas löpande — ren engångs-förifyllning. Befintliga mallar/projekt fick sina tomma kategorifält engångs-backfillade när fältet infördes (2026-08-22). |
| `dagsfokus` | Dagens 1–3 självvalda fokusuppgifter, satta i Börja dagen-flödet. Privat per person (samma RLS-avsteg som Flexel). |
| `dagsavslut` | En rad per person och dag, skapas första gången kvällsflödet öppnas. Finns bara kvar som ankare för `dagsavslut_tanke` — `avslutad_at`-kolumnen finns kvar i schemat men "Avsluta dagen"-knappen som skulle sätta den är borttagen tills vidare (se Öppna frågor). Privat per person. |
| `dagsavslut_tanke` | Fristående reflektionstankar från "Vad skaver?"-steget i Avsluta dagen, med valfri länk till en auto-skapad uppföljningsuppgift. Privat per person. |

## Behörighetsmodell

- Allt scopat per `foretag_id` via RLS. Admin hanterar kunder och personer. `uppgift`, `projekt` och `kategori` är öppna för alla inloggade i företaget på samtliga operationer (inklusive radering) — `projekt` och `kategori` gick tidigare via admin-only-policys men öppnades upp för konsekvens med `uppgift`.
- **Systemadministration** — en egen sida (endast admin) för att skapa/redigera/ta bort uppgiftstyper, kategorier, anteckningsblock (skapa/omordna/avaktivera) och **Projektmallar** (skapa/redigera/ta bort mallar, samt lägga till/redigera/ta bort/omordna uppgiftsmallar inom varje mall), samt en **Användare**-sektion för att redigera namn, roll, Outlook-mail och arbetstimmar/vecka på befintliga personer (inget skapa/ta bort — personer tillkommer via inloggning, inget inbjudningsflöde ännu).

## Byggt hittills

- Kundkontakter med e-post och "senast kontaktad"-status, inklusive ett "planerat möte"-datum härlett från kommande uppgifter kontakten är deltagare i
- Återkommande uppgifter (serier) med redigerbart startdatum utan att generera felaktiga förekomster bakåt i tiden
- Uppgiftstyper och kategorier som admin-hanterade taggnings-listor
- Outlook-kalendersynk (enkelriktad, via webhook): möten skapar/uppdaterar uppgifter automatiskt, tolkar ämnesraden för att tagga rätt kund (konventionen "Kund, QNOVA - Titel"), matchar/skapar kontaktpersoner utifrån mötesdeltagarnas mailadresser, hanterar tidszon (Stockholm/DST) på servern. Hoppar över möten utan riktiga deltagare — mailboxägarens egen adress räknas bort ur deltagarlistan innan filtret slår till, eftersom Outlooks PowerAutomate-trigger listar ägaren som required attendee även på egna, deltagarlösa kalenderblockeringar (t.ex. återkommande "Kundmöte/Kundarbete"-block). ~150 historiska sådana uppgifter, skapade innan filtret fanns, städades bort manuellt.
- Manuell sortering av kort inom samma dagskolumn i Kanban-vyn, utöver drag-and-drop mellan dagar
- Tidsåtgång (timmar) och klockslag på uppgifter, med tidsåtgång som standardvärde på serier
- Snabbare veckonavigering i Kanban-vyn (client-side navigering istället för full omladdning)
- Enhetlig knappdesign, papperskorgs-ikon för borttagning i formulär, scrollbara modaler, mailto-ikon intill kontaktens namn
- Datumfält begränsade till fyrsiffriga år (2000–2099)
- ~140 kunder och ~200 kontaktpersoner bulk-importerade med dublettkontroll och domänbaserad kund-matchning
- Strukturerade mötesanteckningar på mötesuppgifter: admin-hanterade block, autosave (markdown-editor, samma som Beskrivning), och en expanderbar vy som fyller webbläsarfönstret (utan att ta över hela skärmen som F11) för att kunna placeras bredvid ett annat fönster under möten
- "Tidigare möten med kunden" på mötesuppgiften, och en samlad mötesanteckningsvy på kundkortet
- **Rapporter**-sektion i huvudnavet, öppen för alla inloggade (ingen adminspärr). Första rapporttypen: **Tidsrapportering** — registrerad tid grupperad per kund för en vald vecka, med person- och veckofilter (samma vecko-UX som Kanban). Rent läsande, ingen ny tabell — bygger på `uppgift.tidsatgang_timmar`/`deadline`/`kund_id` m.fl. Kategori-fördelningen för veckan visas som klickbara summeringsboxar (en per kategori, samma stil som Flexels saldoboxar) ovanför listan — en box fungerar samtidigt som filter-toggle (klick filtrerar listan på den kategorin, klick igen visar allt). Filtreringen sker client-side (`useState`/`useMemo` på en redan hämtad, ofiltrerad radlista) istället för en ny sidladdning per klick, eftersom en server-rundtripp för varje klick kändes segt.
- Användarkonfiguration i Systemadministration (namn, roll, Outlook-mail, arbetstimmar/vecka). Arbetstimmarna fördelas jämnt över veckans 5 arbetsdagar och visas i Kanban-vyns kolumnrubriker som "planerat/kapacitet" (t.ex. "5h/8h") för inloggad användares egna uppgifter den dagen — ersätter den tidigare summan av allas timmar per kolumn. På halvdagar hårdkodas kapaciteten till 4h istället för veckosnittet; på röda dagar döljs kapacitetstalet helt.
- **Svenska Dagar** ([src/lib/svenska-dagar.ts](../src/lib/svenska-dagar.ts)) — namnsdag/röd dag/helgdagsnamn hämtas från det öppna `api.dryg.net` (inget konto, cachas per år ~1 dygn via Next `revalidate`). Namnsdagen visas i Idag-vyns datumrad på Hem. I Uppgifter-kolumnerna och Flexel-raderna markeras röd dag och halvdag (dagen innan röd dag) med ett diagonalt streckmönster ovanpå standardbakgrunden istället för en egen kulör (grönt/rött krockade visuellt med appens success-/danger-toner) — röd dag täcker hela kolumnen/raden och byter kolumnrubriken mot helgdagens namn, halvdag räknas och täcker bara kortytan (listan med kort, inte rubrikraden) med en tunn delarlinje vid 50%-gränsen.
- **Idag-vyn** — Hem-sidan ("/") ersatt med en tvåkolumns dashboard vars innehåll styrs av tre klockstyrda dagsflöden istället för en statisk hälsning. Vilket flöde som är aktivt avgörs helt av klockslag mot två per-person-inställningar i Systemadministration → Användare (`dagsflode_morgon_slut`/`dagsflode_mitt_slut`, standard 11:00/15:00) — ingen manuell växling. Missad avslutning en dag hanteras tyst: uppgifterna dyker bara upp som eftersläpning nästa morgon.
  - **Vänsterkolumnen**: "Dagens tidslinje" — alla dagens uppgifter (mötesuppgifter och vanliga) i en enda lista sorterad på `sortordning`, samma fält Kanban-vyns drag-and-drop skriver till, så ordningen matchar Kanban exakt (tidsatta och otidsatta rader blandas fritt). Punkt + sammanhängande linje mellan raderna; klockslag visas i en egen kolumn när det finns. Hela raden (utom kryssrutan) öppnar det delade uppgiftsformuläret (se "Konsoliderat uppgiftsformulär" nedan). På kvällen fortsätter samma block med Flexel-snabbregistrering och "Imorgon väntar" (samma punkt/linje-design, men skrivskyddad).
  - **Högerkolumnen**: en ring med "X av Y klara" för dagen, "Gårdagens försenat" (alla obockade uppgifter med deadline före idag, synlig i alla flöden), "Dagens fokus" (välj 1–3 uppgifter, bara på morgonen), "Kunder idag" och på kvällen "Vad skaver?" (fristående reflektionstankar, valfritt kopplade till en auto-skapad uppgift imorgon).
  - Ingen egen "Avsluta dagen"-knapp just nu — fanns tidigare men gjorde bara en sak (satte en tidsstämpel utan koppling till någon annan logik) och togs bort i väntan på en tydligare idé om vad den ska göra.
- **Flexel** — andra fliken i Rapporter (Tidsrapportering | Flexel), personlig logg för Flex, Övertid, Föräldraledig och Ledighet som ersätter en tidigare Excel-fil (242 historiska rader importerade). Tre tabeller (`flexel_post`, `flexel_installning`, `flexel_kvotjustering`), strikt privat RLS på post/kvotjustering (`person_id = current_person_id()`, **ingen admin-insyn** — medvetet avsteg från appens vanliga `foretag_id`+admin-mönster). `flexel_installning` följer däremot det vanliga admin-mönstret (admin sätter Flex/Övertid/Föräldraledig per person i Systemadministration → Användare) — utom **Ledighet**, som är en fjärde typ alla har utan aktivering. Vyn är månadsbaserad (inte veckobaserad): ett dag-rutnät per vardag, grupperat i veckokort, där en vecka hör till den månad dess **fredag** ligger i (samma modell Ivan använde i Excel, matchar hans månadsrapportering till jobbet/Försäkringskassan). Föräldraledig-kvoten (fredagar × veckotimmar per månad, justerbar per månad för undantag) är verifierad mot den ursprungliga Excel-filens egna checkpoint-formler.
- **Projekt** (steg 2 av det tidigare pausade projekt-initiativet) — `projekt`-tabellen aktiverad som container för uppgifter: namn, valfri kund, status, beskrivning, startdatum. Egen toppnivåflik **Projekt** (mellan Uppgifter och Kunder) visad som en Kanban-tavla — en kolumn per projektmall, projekten som klickbara kort (namn, statusbadge, kund/"Internt", "X av Y klara"), egen "+ Nytt projekt"-knapp per kolumn som förifyller mallvalet, plus en global knapp i sidhuvudet. Projekt utan matchande mall hamnar i en egen "Utan mall"-kolumn (visas bara om den har innehåll). Ett tidigare försök att lägga skapa/redigera-flödet i en flik på kundkortet stötte på en nästlad `<form>`-bugg (Modal-komponenten portalar inte) och flyttades därför till egen sida istället för att lappa den delade Modal-komponenten.
- **Projektmallar** (del av steg 3, mallmotor) — Systemadministration → Projektmallar. En mall (t.ex. "Uppstart") har en ordnad lista uppgiftsmallar, omordningsbar via drag-and-drop (hela raden, `@dnd-kit/core` — samma bibliotek och släpp-före/efter-princip som Kanban-tavlan; ersatte tidigare upp/ner-pilar). "Nytt projekt" kräver ett mallval och ett startdatum; vid skapande instansieras mallens uppgiftsmallar som riktiga uppgifter kopplade till projektet — deadline för första uppgiften räknas från projektets startdatum, varje efterföljande uppgifts "dagar efter"-fält räknas kedjat från föregående uppgift i mallen (fältetiketten byter text beroende på position). Dagarna räknas i vardagar, inte kalenderdagar — helgdagar (lördag/söndag) finns inte i appen och visas ingenstans, så `leggTillDagar` hoppar över dem både under själva räkningen och som slutresultat (landar en beräknad deadline på en helg skjuts den fram till nästa vardag), och nästa uppgift i kedjan räknar vidare från det skyddade datumet. Mallistan visar ackumulerad "Dag N" per rad. Ny uppgiftsmall förvalt ansvarig = inloggad person; Beskrivning har samma markdown-editor som uppgifter. Mallformuläret stannar öppet (byter till redigeringsläge) efter att en ny mall skapats, så uppgiftsmallar kan läggas till direkt utan att öppna mallen igen. Både mallarnas uppgiftsmallar och projektens uppgifter hämtas färdigt server-side vid sidladdning (ingen synlig laddningsfördröjning vid öppning).
- **Utökat anteckningsstöd på kundkortet** — två separata sektioner, alla hämtade färdigt server-side i förväg (ingen egen klientfördröjning när kundkortet öppnas):
  - **Mötesanteckningar** (befintlig, oförändrad härledd vy över `uppgift`/`uppgift_anteckning`) visar nu innehållet skrivskyddat formaterat via en ny `MarkdownViewer`-komponent (samma Tiptap/`tiptap-markdown`-uppsättning som redigeraren, bara `editable: false`) istället för rå markdown-text.
  - **Anteckningar** — helt fristående manuella kundanteckningar (`kund_anteckning`): titel, datum, markdown-innehåll, valfritt kopplade kontaktpersoner (`kund_anteckning_deltagare`, återanvänder `DeltagareValjare`-komponenten från uppgiftsformuläret). Klick på en rad expanderar den direkt i redigeringsläge — ingen separat visa/redigera-växling.
- **Placeholder-rader** (v1, byggsten för steg 3/mallmotorn) — löser problemet att en projektmall vill referera till t.ex. "Uppstartsmöte" innan mötet är bokat i Outlook. Flaggan `ar_placeholder` sätts på en uppgiftsmall i Systemadministration → Projektmallar ("Detta är en placeholder"-kryssruta). Vid projektgenerering (`skapaProjekt`) ärver den genererade `uppgift`-raden flaggan och hamnar med rätt `projekt_id`, men visas **aldrig** i Uppgifter-Kanban, Idag-vyn eller Realtime-strömmen (explicit `ar_placeholder=false`-filter på alla tre) — den är bara synlig i Projekt-vyns uppgiftslista, där den fungerar som en väntande platshållare i checklistan. När det riktiga mötet väl finns som en egen `uppgift` (typiskt Outlook-synkad) och den raden redan har fått ett projekt valt i formuläret, dyker en "Koppla till placeholder"-kontroll upp — förfylld synkront från en liten, redan hämtad lista (inget eget nätverksanrop, för att undvika synlig fördröjning), filtrerad till placeholders i samma projekt och av samma typ. Vid koppling (`kopplaTillPlaceholder`): `projekt_id` sätts, `kategori_id` fylls i bara om tomt på den riktiga uppgiften, **`sortordning` tas över** (så den riktiga uppgiften hamnar på exakt samma plats i Projekt-listan som placeholdern hade — annars skulle det verkliga mötets datum, som ofta avviker från vad mallen planerade, kasta ner den längst ner), och placeholder-raden hård-raderas. Projekt-vyns uppgiftslista sorteras på `deadline` (uppgifter utan datum sist), med `sortordning` bara som tiebreak inom samma datum — ändrat tillbaka från en tidigare `sortordning`-först-sortering som höll kvar en kopplad placeholders mall-position även när den riktiga uppgiftens datum avvek kraftigt, eftersom lösa uppgifter kopplade till projektet i efterhand (t.ex. via "Koppla till placeholder", eller genom att sätta projektet på en redan existerande uppgift) annars hamnade fel i listan. Ingen automatisk matchning eller städning av obehandlade placeholders i v1 — rent manuellt.
- **Anteckningsmallar** — ersätter den tidigare enda globala blocklistan. `anteckningsblock` grupperas nu under `anteckningsmall` (Systemadministration → Anteckningsmallar, samma två-nivåers UI-mönster som Projektmallar); block skapas alltid inom en specifik mall, ingen delning mellan mallar. Blocklistan omordnas via drag-and-drop (samma mönster som Projektmallars uppgiftsmallar), och varje block kan ha en kort `beskrivning` som visas som hjälptext under labeln när man faktiskt antecknar — tänkt som en instruktion till sig själv om vad som ska samlas in under mötet. `uppgiftstyp` ("Visa anteckningar", tidigare `visar_motesanteckningar`-kryssrutan) pekar nu ut vilken mall som är standard för typen istället för att bara slå på/av en delad blocklista. Vilken mall en enskild uppgift faktiskt visar avgörs av `uppgift.utan_anteckningsmall ? null : (uppgift.anteckningsmall_id ?? uppgiftstyp.anteckningsmall_id)` — men det fältet på uppgiften går **inte** att ändra i Mötesanteckningar-sektionen (för att undvika föräldralösa anteckningar när blocken byts ut under en uppgift som redan har innehåll). Enda sättet att avvika från typens standard är via `mall_uppgift.anteckningsmall_id`/`utan_anteckningsmall` i Projektmallar (dropdown med "Använd typens standard" / "Ingen mall" / en specifik mall), satt innan några riktiga anteckningar finns, och kopierat till den genererade uppgiften vid `skapaProjekt`. Migrering: alla befintliga block samlades i en ny "Standard"-mall, och uppgiftstyper som redan hade mötesanteckningar påslagna fick den som sin standardmall. `kopplaTillPlaceholder` kopierar nu även `anteckningsmall_id`/`utan_anteckningsmall` (samma "fyll bara i om tomt"-mönster som `kategori_id`, förutom att `utan_anteckningsmall` bara ärvs när placeholdern uttryckligen är `true`) — annars behöll en Outlook-synkad uppgift som kopplades till en placeholder med avvikande anteckningsmall typens standard istället.
- **Projektanteckningar** — separat modul från `uppgift_anteckning`, byggd för att lösa att en levande spec (t.ex. från ett kundmöte) behöver synas på flera olika uppgifter inom samma projekt istället för att bara finnas på mötesuppgiften. `mall_projekt.anteckningsmall_id` sätter projektets **gemensamma, delade** anteckningsmall (ärvs via `projekt.mall_projekt_id` — inget eget fält på `projekt`); innehållet lagras i `projekt_anteckning`, en rad per block och projekt. Visas och redigeras identiskt från tre ställen — projektets egen redigeringsmodal, en uppgifts formulär i Projekt-vyn, och uppgiftsformuläret i Uppgifter-Kanban/Idag-vyn — via samma `ProjektAnteckningarSektion`-komponent, med samma fullskärms-anteckningsläge (liten ikon i höjd med rubriken) som `MotesanteckningarSektion`. Helt oberoende av `uppgift_anteckning`: en meeting-uppgift i ett projekt kan ha *båda* — sina egna, uppgifts-lokala anteckningar (om typen/uppgiften inte är satt till `utan_anteckningsmall`) och projektets delade anteckningar samtidigt, i separata sektioner. Historik/versionering (vem ändrade vad, och när) är medvetet inte byggt än — väntar tills behovet är konkret.
- **Klickbara uppgifter i Projekt-vyn** — i "Redigera projekt"-modalen öppnar ett klick på en uppgiftsrad det delade uppgiftsformuläret (se "Konsoliderat uppgiftsformulär" nedan) istället för ett projekt-specifikt formulär. Byter vy istället för att nästla ett andra `<Modal>`/`<form>` i det redan öppna projektformuläret — samma mönster som Projektmallars uppgiftsmall-redigering. Sparas via samma `uppdateraUppgift` som resten av appen; den öppna modalens egen uppgiftslista laddas om via `hamtaProjektUppgifter` (skickas in som `onChanged`), så "X av Y klara" och raden uppdateras direkt utan att stänga modalen.
- **Konsoliderat uppgiftsformulär** (2026-08-22) — tidigare fanns tre olika komponenter för att skapa/redigera en uppgift (fullständig i Uppgifter-Kanban, en minimal variant på Hem, en tredje i Projekt-vyn) och Rapporter → Tidsrapportering saknade redigering helt. Slogs ihop till en enda delad komponent, [`UppgiftFormular`](../src/app/uppgifter/uppgift-formular.tsx), använd på alla fyra ställen. Ny fältgruppering i formuläret: Titel/Beskrivning överst (oförändrat), följt av gruppen **Kund** (Kund, Projekt, Deltagare) och gruppen **Kategorisering** (Typ, Kategori på samma rad; Prioritet och Status därefter var för sig, egen rad var). Konsekvens av att det verkligen är samma komponent överallt: Hem, Projekt och Tidsrapportering fick automatiskt funktioner de saknade tidigare (ta bort-knapp, byta ansvarig, "Gör återkommande", byta kund/projekt/typ/kategori/deltagare) — och en uppgiftsrad i Tidsrapportering går nu att klicka och redigera, vilket inte var möjligt innan.
- **Projektfärg** — färgväljare i "Redigera projekt" (`projekt.farg`), en fast palett av 18 namngivna toner (hela Tailwinds standardfärghjul + grå) istället för fri hex-input, så varje val garanterat har definierade ljust/mörkt-läge-varianter och matchar en CHECK-constraint i databasen. Markeringen av vald ton ritas som en `ring` direkt på swatchen (box-shadow, alltid koncentrisk) snarare än en nästlad border+prick-struktur. Uppgiftskorten i Uppgifter-Kanban (även drag-släpp-förhandsvisningen) tonas nu i projektets färg som en ljus/mörk bakgrundston, medan projekt utan vald färg behåller standardytan (`bg-surface`). Kortens kontextrad ovanför titeln ("brödsmulan") visar Kategori i mittpositionen oavsett om uppgiften hör till ett projekt eller inte (Kund · Kategori · Typ) — projektmallens namn/"projekttyp" visades där tidigare för projektuppgifter, men togs bort igen eftersom Kategori ger konsekvent brödsmula oavsett projekt.
- **Projektets Beskrivning** i "Nytt/Redigera projekt" bytt från vanlig `Textarea` till samma `MarkdownEditor` som uppgifters Beskrivning, för konsekvent md-stöd (rubriker, fetstil, listor, länkar) över hela appens beskrivningsfält.
- **Kontaktperson och kundanteckningar i egna modaler** — kontaktpersonens formulär (`KundFormular`, early return) och de manuella kundanteckningarnas redigeringsformulär (`KundManuellaAnteckningarSektion`) öppnas nu i varsin egen `<Modal>`, samma mönster som Projektmallars uppgiftsmall-redigering och Projekt-vyns uppgiftsrader, istället för inbäddat direkt i kundformuläret. Åtgärdar att kundens egen radera-ikon låg synlig samtidigt som kontaktpersonens/anteckningens, vilket ledde till att hela kunden raderades av misstag när avsikten var att radera en kontaktperson (eller en anteckning). Klick på en kontaktperson direkt i Kunder-listan (utan att först öppna kunden) öppnar dess modal helt fristående (`redigerarFristaendeKontakt` i `KundVy`) istället för att som en bieffekt öppna kundmodalen bakom — annars låg kundmodalen kvar synlig när man stängde kontaktens modal, trots att man aldrig bett om att se kunden.
- **Ta bort serie och alla uppgifter** — `SerieFormular` hade sedan tidigare bara en "koppla loss"-radering (`taBortSerie`, papperskorgsikonen i modal-headern): tar bort `uppgift_serie`-raden men lämnar redan skapade uppgifter kvar som vanliga uppgifter. Ny röd länk "Ta bort serien och alla uppgifter" (samma placering/stil som Projekt-vyns motsvarande länk — egen rad ovanför knappraden, `self-start` eftersom formuläret är en flex-column och annars stretchar/centrerar länken) räknar först antalet kopplade uppgifter (`raknaSerieUppgifter`) för bekräftelsetexten, och kör vid bekräftelse `taBortSerieMedUppgifter`: raderar alla `uppgift`-rader med matchande `serie_id`, sedan själva serien. Går inte att ångra.
- **Beskrivning/anteckning-ikon i Kanban-korten** — en liten dokument-ikon (samma inline-SVG-mönster som papperskorgs-/mailto-ikonerna) visas intill tidsåtgången när uppgiften har en ifylld Beskrivning eller minst en mötesanteckning med innehåll, så det syns direkt i kortvyn utan att öppna uppgiften.

## Medvetna förenklingar / avgränsningar just nu

- `projekt_medlem` fortfarande oanvänd — inget sätt att sätta en projektägare oavsett vem som är ansvarig på de enskilda uppgifterna
- Projektmallar stödjer inte checklistpunkter (steg 1 i det ursprungliga initiativet, inte byggt) och genererar inga kopplingar till återkommande uppgifter
- Projektnamn föreslås inte automatiskt utifrån mall + kund vid skapande — skrivs manuellt varje gång
- Kontaktperson har bara namn, e-post och senast kontaktad — inget telefonnummer, roll/titel eller egen kontaktlogg
- Outlook-synken är enkelriktad (Outlook → Jobbet), inte via inloggning — Google är fortfarande enda inloggningsmetoden
- Inget inbjudningsflöde för kollegor ännu
- Ingen notifieringslogik i appen (mejl/push)
- Ingen mobilanpassning testad
- Ingen AI-transkribering av fritext/ljud till anteckningsblock
- Anrop till Postgres-funktioner via `supabase.rpc(...)` kollar inte returnerat fel i koden — en trasig DB-funktion (t.ex. `generera_serie_forekomster`) misslyckas då helt tyst i UI:t. Hände 2026-08-17–21: kolumnen `uppgiftsprojekt_id` döptes om till `kategori_id` (migration `rename_uppgiftsprojekt_till_kategori`) men funktionen uppdaterades inte, så nya serieförekomster slutade genereras utan felmeddelande. Rättat i funktionen; själva felkontrollen i klientkoden är fortfarande inte byggd.

## Öppna frågor att diskutera

- Ska `projekt_medlem` aktiveras för att kunna sätta/se en projektägare oavsett enskilda uppgifters ansvariga?
- Ska projektmallar kunna definiera checklistpunkter (steg 1 i initiativet)?
- Ska projektnamn föreslås automatiskt (mall + kund) vid skapande, eller är manuellt bra nog?
- Behöver kontaktpersoner fler fält (telefon, roll/titel)?
- Ska Outlook-integrationen byggas ut (tvåvägssynk, felhantering/synlighet vid misslyckad synk)?
- Hur ska inbjudningsflödet för kollegor se ut?
- Behövs notifieringar till användare, och i så fall via vilken kanal?
- Ska Kanban-vyn fungera på mobil?
- Tidsrapportering v1 är byggd (vecka × kund); en uppgiftsrad går nu att klicka och redigera (inkl. tidsåtgång) via det delade uppgiftsformuläret. Utanför scope hittills: export (PDF/Excel), inline-redigering direkt i rapporttabellen, filter på flera personer samtidigt, månads-/årsvy, historik/trend över tid, koppling till "senast kontaktad" eller andra kundfält — värt att prioritera bland dessa vid nästa iteration.
- Flexel: Ivan funderar på att bokföra *varje* vardag (0h + motivering på vanliga dagar, typ mindre relevant), inte bara avvikande dagar — medvetet skjutet på framtiden tills det visar sig relevant.
- Flexel: `flexel_kvotjustering` (manuell kvotminskning per månad) och den nya typen Ledighet (fristående daglig logg) överlappar delvis i syfte — värt att fundera på om kvotjustering kan fasas ut till förmån för att bara logga Ledighet-rader, nu när båda finns.
- Idag-vyn: vad ska "Avsluta dagen" som handling faktiskt innebära (utöver att vara en tidsstämpel)? Tidigare variant gjorde ingenting kopplat till kvarvarande uppgifter, streak eller liknande — togs bort tills det finns en tydligare idé.

## Arbetsflöde för Claude Code

- Använder inte subagents som standard — endast vid uttrycklig begäran eller bred undersökning, och motiverar då i en mening innan den startar.
- Direktkopplad till Supabase via MCP — fattar egna beslut om tabeller, migrations, filstruktur utifrån kraven.
- Committar per logisk delleverans — pushar inte automatiskt, bara vid uttrycklig begäran eller när Claude Code rekommenderar det och användaren godkänner.
- Har projektspecifika regler i `CLAUDE.md` för UI-granskning, databas-konsistens och multi-tenant-scoping som måste följas vid relevanta ändringar — några tillhörande skill-filer är kända att vara kopierade från ett annat projekt och väntar på omskrivning.
- Stämmer av oklarheter med användaren innan implementation påbörjas.
